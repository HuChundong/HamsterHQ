# 定时任务

[English](scheduled-tasks.md) | 中文

租户让 agent 晚点做一件事——一次、在某个时刻、或者按某个周期——然后它就会发生,
不管人在不在看,也不管那一刻他的沙箱还存不存在。这一页说清楚这件事的每一部分住在
哪里、为什么那个时钟不在两个看起来最顺手的地方,以及一次到期究竟做了什么。

这里的东西一行都还没写。之所以写在代码之前,是因为形状才是那个贵的决定:时钟住在
哪里,决定了重启之后什么能被恢复;之后再搬,搬的是持久状态。

## 一句话

**一个服务拥有"什么时候",网关拥有"你是谁"和"把机器叫醒",一个插件拥有"机器起来
之后干什么"。**

这句话就是判据。一个改动会被问它属于三者中的哪一个;同时属于两个的改动,位置错了。

## 时钟为什么不能住在沙箱里

harness 本身就带 `@deepseek-ai/dsh-schedule`,这个部署也已经装上了——它是
`@deepseek-ai/dsh` 的依赖——但没有任何 composition 挂载它。这是刻意的,理由写在它
自己的文档里:

- **只在会话内投递。** 提醒只在它原本那个 Session 活着的时候准点运行;一个冷的
  Session 收不到任何外部通知,只有被 resume 之后才会处理一条已经过期的记录。
- **加载顺序的边界。** 插件不会扫描或接管在它加载时就已经活着的 Agent。

所以它的状态是持久的——记录写在 Session event log 里,落在卷上——但恢复是懒的。
沙箱重启后什么都不读,直到有人重新打开那个会话。对于 dsh 就跑在使用者桌面上的场景,
这是正确的设计。而在这里,标签页关掉五分钟后沙箱就被回收,于是"Session 活着的时候"
约等于"有人在看的时候",而这恰好是定时任务唯一不需要的那种情况。

更深的那个理由,就算沙箱永不销毁也仍然成立。每个沙箱里一个时钟,就是每个租户一个
时钟,于是**没有任何组件能回答"接下来五分钟要触发哪些"**——答案散在两千个进程里,
其中大多数没在运行。调度本质上是一张有序的表,被一个读者读,而这不是一个按租户存在
的进程能扮演的角色。

`dsh-schedule` 保持不挂载,而不是挂载了再绕开。同一条提醒有两份记录——一份在
Session 日志里,一份在数据库里——就变成了对"它到底跑没跑"的两种说法,而租户分不出
哪个是当前的。

## 时钟为什么也不住在网关里

网关是唯一能启动沙箱的组件,所以触发最终必须到达它。这让它看起来是顺手的家,但它是
错的那个。

`gateway/` 认证每一个租户,并且持有 Docker socket,而那等价于宿主机的 root。一个
调度器需要的只是:一个数据库、一个时钟、一个说"就现在"的出口。它不需要 Docker
socket,不需要租户凭据,也不需要面向浏览器的界面。这是一组严格更小的权限,而这个仓库
已经做过一次同样的判断:运维控制台是它自己的服务、拿它自己的凭据,而不是网关里的一
个章节。

还有第二个更实际的理由。调度器是这个功能里会反复改的那部分——时区、夏令时、cron
表达式的边界、补偿策略——而网关是登录路径。一个改动频繁的组件,不应该和一个改坏了
就让所有人登不进来的组件共用进程。

所以:第五个服务,`scheduler/`,只在内网。没有 nginx location 指向它,浏览器到不了
它。

## 四个部分,各自拥有什么

| 部分 | 拥有 | 永远不知道 |
|---|---|---|
| `scheduler/` | 任务表、cron 与间隔规则、下一次时刻的推算、补偿策略、运行历史 | 租户除了一个不透明 id 之外是谁;沙箱怎么启动 |
| `gateway/` | 哪台沙箱属于谁、怎么启动一台、启动要多久 | 一个 cron 表达式是什么意思;一个任务的 prompt 说了什么 |
| `packages/dsh-scheduled-tasks` | 模型看到的那三个工具,以及把一次到期变成一轮 turn | 任何东西什么时候到期 |
| Postgres | 一如既往,唯一的那个存储 | — |

网关里**没有 cron 代码,也没有任何针对任务表的查询。**这一条是可以被强制的而不是靠
记住:一个检查在 `gateway/src` 里 grep 任务表的表名和 cron 依赖,命中任何一个就失败。

调度器的表就住在这个部署唯一的那个数据库里,由它自己的 `db.js` 在启动时 apply,和
网关的做法一样。第二个存储被考虑过、被否掉了,理由和当初否掉第一个一样:那意味着第
二份备份、第二种失败模式,以及对"这个部署的数据安全吗"的两种答案。

## 三条链路,每条用与自己形状相配的方式

**写入——沙箱发问,走 HTTP。**插件的工具不做任何决定。它们带着 `x-sandbox-id` 和
`x-sandbox-token` POST 给网关,也就是 `/_tunnel` 已经在授权的那一对,网关从
`sandboxes` 表反查出属主租户。**沙箱从来不指名租户**,所以一台被攻陷的沙箱写不进别
人的日程。网关把租户身份和那个租户的 entitlement 记录盖在请求上,转发给调度器;调度
器校验规则、算出第一次时刻、答复。网关只读到够转发为止。

这需要在沙箱环境里加一个变量,就放在 `sandboxes.js` 里 `GATEWAY_TUNNEL_URL` 旁边。
显式传而不是从隧道 URL 推导:从 `ws` 推 `http` 一直是对的,直到某个部署把隧道放在
一个路径后面或者第二个域名上——那时它就错了,而且只会在生产上现形。

**唤醒——网关推送,走隧道。**当一次到期进入调度器的视野窗口,它给网关打一次调用:
这个租户、这一次、到期在这一刻。网关立刻答 `accepted`,然后用它自己的计时器,提前
到足够早的时候把机器拉起来——提前多少是网关的知识而不是调度器的,因为那是关于
runtime 的事实,换了 runtime 就会变。等沙箱 dial in 之后,网关在已有的隧道上发一个
新的下行帧,由 `dsh-gateway-tunnel` 转成一个 cordis 事件重新发出。加一种帧是构造上
安全的:沙箱本来就会忽略它不认识的 tag,"so the gateway can add frame kinds without
a lockstep sandbox-image rebuild"。

用推送而不是轮询,理由和指标平面那条一样:polling per sandbox 正是 push 模型取代掉
的东西,两千个沙箱会让一次轮询变成负载问题。

**运行——插件来拉,然后回报。**那个 nudge 不携带 prompt。收到它之后——以及在自己
启动时也做一次,这就是恢复机器停机期间错过的工作的那条路——插件回头穿过网关去取属
于自己的到期项,跑完,再用同样的方式回报每一次的结果。于是网关从不携带租户的任务内
容,而沙箱"重启后补上"的路径和"你现在有活了"的路径是同一段代码,而不是第二套更少被
走到的机制。

提前量有一条硬约束:必须小于 `SANDBOX_DEPARTED_TTL_MS`,默认五分钟。比这更早启动的
机器,没有浏览器附着、也没有 agent 在跑,会在自己的任务到达之前先被空闲回收扫走。

## 一次到期具体做什么

插件**新建一个会话**并向它发 prompt,而不是 resume 任务被创建时的那个会话。

两种都考虑过。Resume 保留上下文,而这正是提醒之所以像提醒的原因——同时它让一份
transcript 无限增长,让每一次运行都依赖一份旧的 Session 日志仍然可加载,并且把一个月
的无关历史摆在一个只被要求查一件事的模型面前。新会话是一份干净、可读、恰好记录这次
运行做了什么的记录,并且除了任务那一行之外不依赖任何东西。

代价明说而不是藏起来:**各次运行互相不记得。**一个需要知道上次运行发现了什么的任务,
得把它写进 workspace——那是持久的,下一次运行读得到。

turn 运行期间,隧道会报 `activity`,空闲扫描会跳过这台沙箱——`presence?.busy === true`
在两个 TTL 之前就被检查了。跑完之后没有任何东西附着,机器会被普通的扫描回收。这里
不需要任何特例。

## 当任务很频繁

一个间隔比空闲扫描的耐心还短的任务,永远不会放开它那台机器。于是唤醒这一步在大多数
到期上什么都没做:沙箱本来就起着,网关直接跳到 nudge,剩下的东西看起来就像一个跑在
恰好还活着的进程里的定时器。

这种塌缩是设计在正常工作,而不是在失效。唤醒是一个**有条件的步骤**,每次到期问一
句:这个租户的机器起来了吗——所以两种情形是同一段代码里带一个分支,而不是两套设计。
没有变的是真相在哪里:任务、它的规则、以及"该不该触发"这个决定,两种情形下都在调度
器里;一台中途死掉的机器,恢复走的也是和从未起来过的那台一样的路。

错的是那条边界。今天它是从 `SANDBOX_DEPARTED_TTL_MS` 里掉出来的——一个为了完全无关
的理由选的常数:有人关掉标签页之后还留机器多久。运维出于和调度毫无关系的理由把它从
五分钟调到两分钟,就会悄悄把一批任务从"温的"挪成"每次运行都冷启动"。两个从来没打算
互相作用的旋钮,最后决定了一个它们都没提到的功能的成本和延迟。

两个修正,而且与其说是新机制,不如说是关于既有机制的一条规则。

**谁叫醒的,谁负责放回去。**一次定时运行结束时,网关立刻释放沙箱,而不是丢给空闲扫
描;用 `presenceOf` 已经返回的那两个信号做闸——有浏览器附着、或者还有 agent 在跑的
机器,不碰。没有这一条,每次运行都会白漏一整个 departed TTL 的机器时间,对一个每小时
的任务就是每六十分钟浪费五分钟。

**最短允许间隔从唤醒的成本推导出来**,而不是从上游抄。只要这个下限高于 departed
TTL,任何日程都不可能靠自己把机器焐热,就只剩一个 regime 而不是两个,一个任务的成本
可以从它的规则算出来。所以这个下限是每个部署自己的数字,绑在它 runtime 的启动耗时
上,而不是 harness 自己的调度器恰好用的那五分钟。

**下限以下的不是定时任务。**每三十秒必须发生一次的工作要的是一个进程而不是一个日
程,而 dsh 已经有了:`ctx.jobs` 已经挂载,`job_list`、`job_output` 和 `job_kill` 已
经摆在模型面前。它的诚实正是关键——一个 job 活在内存里,随沙箱一起死,所以要一个
job 就等于要一台一直开着的机器,而那应该是租户显式做出并为之付费的决定,而不是把间
隔设得太小的副产品。

## 至多一次,而错过会被记下来

一次到期**至多被派发一次**,而没有发生的那一次会被写下来"没有发生"。

另一种做法——重试直到被确认——对这种载荷是错的。一次运行会花掉模型 token 并写入租
户的 workspace,所以重复不是一条重复的消息,而是一次副作用的二次执行。租户看得见的
一次错过是可以补救的;一次静默的重复运行不是。

具体地说:调度器在网关答 `accepted` 时推进 `next_run_at`,并把那一次记为 in flight
带一个截止时间。到达的结果会写进去。截止时间过了还没有结果就写 `lost`——网关在
accept 和实际投递之间重启,看起来就是这样,而它对租户是可见的,而不是从一份空白的
transcript 里去猜。在派发时而不是在完成时推进,是为了让一次卡住的运行不会把后面每
一次都堵在它身后排队。

错过的那些不会被回放。停了六小时的部署恢复后,每个任务在它下一次时刻运行一次,而不
是六次——和 harness 自己的调度器出于同样理由定下的规则一致。

## 租户被允许什么

一个定时任务会在没人看着的时候花掉模型 token,这让它成为这个部署里第一件能在主人睡
觉时产生费用的东西。三个限制,全部从 `entitlements.js` 解析:一个账号能持有多少个任
务、两次之间最短的间隔、每天最多跑多少次。

网关来解析它们,因为 entitlements 本来就在那里解析,并把它们附在被转发的请求上。调
度器来执行它们,因为执行意味着拿它去和一条 cron 规则比较,而网关不知道那是什么。
`check-entitlements.mjs` 要求在那里声明的字段必须在 `gateway/src` 的某处被读到;附上
去就是那次读。

## 在哪里看得见

两个界面,而这个分法来自"沙箱大部分时间是关着的"这个事实。

**网关提供列表**,在它自己的页面上。它是机器没在运行时唯一还能用的界面,而那恰好正
是租户会来问"为什么那件事没发生"的时刻。它显示每个任务、下一次时刻、以及最近几次运
行的结果,并且能删掉一个。

**shell 里显示同一份列表,只读**,由插件提供,就在那三个工具旁边。一个正在看自己会话
的租户,不该为了看有哪些定时任务而离开会话;一个沙箱已经没了的租户,不该为此先起一
台。

## 刻意不做的事

| 不做 | 为什么 |
|---|---|
| 挂载 `@deepseek-ai/dsh-schedule` | 一条提醒两份持久记录;见上文 |
| 把 cron 放进沙箱或网关 | 只有一个时钟,而且不在那个持有 Docker socket 的进程里 |
| 重试直到被确认 | 重复的运行就是重复的副作用 |
| 回放错过的积压 | 停机六小时不等于六次运行 |
| 秒级/亚分钟的周期 | 叫醒一台机器要几十秒;比唤醒还细的周期是一个没有机制的承诺 |
| 时间以外的触发条件 | webhook 或文件变化触发是另一个主题、另一种失败模型,会在两者都没做完之前先被折进这一个里 |

## 需要改哪些地方

- `scheduler/` —— 新目录和新镜像:`src/server.js`(内部 API,没有公开面)、
  `src/db.js`(它自己的表)、`src/clock.js`(扫描)、`src/rules.js`(cron、间隔和绝
  对时间的推算),以及它自己的 `AGENTS.md` 一对。一个 cron 解析依赖,只在这个服务里。
- `gateway/src/` —— 一条由沙箱那对凭据授权的中转路由;一个 `/_internal/*` 触发端点,
  沿用共享密钥那套做法、密钥不对时答 404 而不是 403;待唤醒的计时器;以及租户的页面。
- `packages/dsh-scheduled-tasks` —— 第六个插件。是新包而不是长在现有插件上:把网关
  拿掉它一行都不成立,这排除了 `dsh-sandbox-host`;它又不是"谁登录了",这排除了
  `dsh-tenant-account`。
- `packages/tunnel-protocol` 和 `packages/dsh-gateway-tunnel` —— 一种下行帧,转成事
  件重新发出。隧道的主题仍然是传输。
- `compose.yml`、`Dockerfile`,以及 `scripts/check-service-env.mjs`——它今天追的是网
  关和控制台两条 import 链,得学会第三条。

## 怎么验证

`scripts/` 决定不了这里的大部分内容,因为每一条有意思的断言都需要一个运行中的部署。
它能决定的有两件,而且都很便宜:`gateway/src` 里没有 cron 依赖、也没有任何指名调度器
表的查询;以及新服务的环境变量在每一处读它的地方都被声明了。

验收套件会多一个 `verify/verify-schedule.mjs`,它的形状由"什么才值得证明"决定:用这
个部署允许的最短间隔建一个任务,**把沙箱销毁**,然后等。通过意味着机器自己回来了、
并且那一轮 turn 跑完了。任何不先销毁沙箱的做法,只证明了容易的那一半。
