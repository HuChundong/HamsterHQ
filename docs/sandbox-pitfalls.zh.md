# 把 agent 放进沙箱，实际要付的代价

[English](sandbox-pitfalls.md) | 中文

这里每一条都是真把这套部署搞坏过的东西，附上暴露它的现象，以及最终定性的那个测量值或报错。
按所属层次分组——因为那决定了谁能修它。

有几条连同「正确结论之前那个错误结论」一并记下。那几条才是有用的：故障从来不在它看起来在的地方。

## 模板是镜像**运行中**状态的快照

CubeSandbox 的模板不是镜像。它是镜像运行时拍下的快照，为每个租户还原一次——所以 `CMD` 启动的
任何东西都会被冻进去，在任何租户存在之前就启动了，且每个还原出来的沙箱里一模一样。

第一版把后端放进了 `CMD`。沙箱起来时带着一个在**另一台机器的生命周期里**启动过的后端，持有
另一台机器的状态，然后立刻退出。当时的直觉——多往模板里烘焙一些东西好让启动更快——恰好是
反的：模板装不下任何「只有租户到来时才知道」的东西。

因此镜像不声明 `CMD`。`cube-entrypoint.sh` 只守着 envd，由网关在拿到那份只在创建时才存在的
身份之后，通过 envd 的进程 API 为每个租户启动后端。

这条规则是一道判据，不是一刀切。后端仍然通不过（身份、挂载、隧道 URL），绝不能冻结。不含租户状态的显示栈——TigerVNC、KDE Plasma X11 和 noVNC——能通过。有头 Chrome 不再能通过：只有让 profile 跟着租户持久卷，登录状态才有价值，而制作通用模板时这个卷并不存在。Cube 0.7 的 `create-from-image` 接受 `--cmd` 与 `--probe`；desktop 镜像用 `/app/sandbox/template-warm.sh` 和 `:6099/health` probe，让显示进程已经在内存快照里。还原之后 `start-desktop.sh` 幂等：端口已在听就是空操作。轻量模板仍在每次后端启动时用 `start-browser.sh` 拉起无头 Chromium。

探针必须描述可见桌面，而不是只描述传输端口。曾经的探针只检查 noVNC 与 CDP，导致 KDE 模板在 Plasma 和 Fluent 主题还在启动时就被截取；每个租户恢复后都要目睹剩余启动过程。现在必须等 Xvnc/noVNC、Plasma、KWin 和主题标记全部就绪并稳定 5 秒，才允许制作快照。Chrome 是刻意缺席的，因此探测 CDP 反而会唤醒它，并把不属于任何租户的 profile 状态重新塞进模板。

把 profile 放到持久卷是必要条件，但它本身并不能保证刚完成的登录已经耐久化。第一次持久化探针在 profile 里写了一个标记，并在第二台 Cube VM 看见它，于是错误地以为已经完成；真实 cookie 却不存在，因为第一台 VM 被销毁前 Chrome 还没有提交它。现在回收会先请求浏览器 `Browser.close`，并只等待一个有上限的时间。验收必须在第二次冷恢复后读取真实的持久 cookie，不能再用任意文件推断登录状态已持久化。CDP 消失也不是 flush 边界：`Browser.close` 会先关闭这个套接字，持有 profile 的进程稍后才释放 SQLite 数据库，而网络文件系统还可能把已经完成的写入留在客户端缓存。因此 stop 路径会等待所有非僵尸 Chrome 进程退出，并在回收前执行有上限的文件系统 sync。

这版增强探针最初又犯了一个更严重的错误：每 500ms 裸连一次 `:5900`。Xvnc 会把未完成 RFB 握手就断开的客户端计为失败，数次后将回环地址加入黑名单，而 Cube 又如实把这份黑名单冻进了模板。租户恢复后，noVNC 因此要等待约 20 秒才能连接 Xvnc。正确方式是检查 Xvnc 进程和 X11 显示是否就绪；不能靠打开套接字后丢弃握手来探测有状态协议。

此前错误的结论：运行手册曾照着 E2B 的 `template build` 写过 `--start-cmd` / `--ready-cmd`，当时的 CLI 两个都没有，浏览器就被挪到每次后端启动上。这段历史对轻量镜像仍然成立；desktop 路径用的是 Cube 后来真正长出来的参数。

**多花一轮才发现的推论：** `POST /templates/{id}` 不会拾取新镜像。把已有模板指向新镜像，每个
沙箱还原的仍是它原来那份快照。换镜像就必须建新模板，每次都是。

## envd 交给进程的是一个干净环境

后端从 `CMD` 改由 envd 启动之后，Dockerfile 里每一行 `ENV` 都悄无声息地不再抵达它。后端跑在
`HOME=/root`、没有权限模式的状态下——也就是说，它在一个「存在的意义就是被随便写」的容器里，
带着没有任何浏览器能回答的审批提示运行。

没有任何东西大声报错。沙箱起来了，隧道拨通了，然后第一次工具调用挂在一个无处可去的提示上。

现在镜像把自己的环境投影进一个文件、由入口脚本 source。这个文件是从**值**生成的而不是重写一遍，
所以它不可能与仍然是唯一出处的那些 `ENV` 行漂移：

```dockerfile
RUN for name in PATH DSH_BIN DSH_HOME IMAGE_DSH_HOME MOUNT WORKSPACE SANDBOX_LAYOUT_VERSION HOME DSH_PERMISSION_MODE NODE_ENV \
                NODE_EXTRA_CA_CERTS TZ VIRTUAL_ENV MPLBACKEND MPLCONFIGDIR \
                OFFICECLI_SKIP_UPDATE DSH_BUNDLED_SKILL_DIR; do \
      printf 'export %s=%s\n' "$name" "$(printenv "$name")"; \
    done > /app/sandbox/env.sh
```

`TZ` 是很晚才加进这个列表的，而且只是因为——每个文件的时间都差八小时，总会有人发现。

## 网络默认拒绝运行它的那套基础设施

CubeSandbox 默认允许公网出站，同时把私有网段一并拒绝，使沙箱无法借它的互联网访问去够到托管它
的基础设施。而网关恰好落在这些网段之一：于是沙箱够得到模型 API，却够不到启动它的那个东西。

网关的地址在创建时被显式放行，与附加网络策略是同一次调用。是地址而不是域名：`allowOut` 里的
DNS 名只有在配合 `0.0.0.0/0` 全拒规则时才生效，而那条规则会把其余一切一起拒掉。

## 模型密钥可以扣下，但没法「有条件地」扣

CubeEgress 终止 TLS 来改写 `Authorization` 头，因此沙箱里拿到的是占位符，真实密钥从不进入。
这一点要紧，是因为里面的 agent 以租户的名义拥有完全权限：环境里、文件系统里、进程表里的任何
东西，都是能被提示词读回来的东西。而一个从来不在那里的密钥，读不回来。

试图在这上面做聪明事，撞出两条约束：

- **拦截以信任为前提。** CubeEgress 为请求的 SNI 现签叶子证书，所以沙箱必须信任该安装自己的
  根证书——而 Node 只验它自带的根、忽略系统信任库，所以光装 CA 还不够，还要 `NODE_EXTRA_CA_CERTS`。
- **注入不能有条件。** 本意是只在请求带着占位符时才注入，这样自己配了密钥的租户不会被覆盖。
  但 `ngx.req.clear_header` 总是先执行，等规则能去看的时候，已经没有东西可看了。
- **宿主机 LOCAL 目标永远进不了 CubeEgress。** 宿主机 `local` 路由表优先级是 0，排在
  TPROXY 策略规则之前。对本机 LAN 地址（`192.168.2.192`）实测：仅 L7 规则时约 2 ms 拒
  SYN，TPROXY 计数不动；同一 IP 再进 `allowOut` 则走 SNAT、能通但不注入。Docker 网桥
  地址即使有 `allowOut` 仍超时。能打进 inject 的是非 LOCAL 的 model relay
  （netns 里的 `10.201.0.2`）——在下面这条路径健康时，连自定义端口 `:8088` 也可以。
- **正在注入时不要把同一主机写进 `allowOut`。** L7 allow 规则本身就会打开该目的地；再写
  一条匹配的 `allowOut` 会并行装上 SNAT，可能在 MITM 之前把流量抢走。因此
  `gateway/src/egress.js` 只在**不**注入时才把私网模型地址放进 `allowOut`。
- **宿主机上宽泛的 `CONNMARK --restore-mark` 会抹掉 CubeEgress 的 mark。** 本机为
  Clash/mihomo 共存写的脚本曾对 mangle PREROUTING 里所有 ESTABLISHED 包做
  connection-mark 恢复，结果把 CubeSandbox 的 L7 mark（`0xce010000` /
  `0xce020000`）盖成 0：SYN 仍进 TPROXY，HTTP 数据到不了 cube-egress nginx（客户端
  重传后 RST），inject 审计停更。恢复必须收窄到仅 WAN mark（`connmark match 0x1234`），
  或排除 `cube-dev`。当时 mihomo 的 TUN 是关的；伤到数据面的是 iptables 副作用，不是
  TUN 本身。
- **明文端点可以被注入，代价也在明处。** 网关生成的规则只在 `https` 时带 SNI——否则没有握手
  可以从中读出它——CubeSandbox 自己的规则构造也是这么分的。`http` 端点付出的代价是 CubeEgress
  到端点这一跳：凭据在那段路上是明文。它仍然不进沙箱，那才是真正值得保住的性质；这一跳明不
  明文能不能接受，取决于端点在哪儿——同一台机器上的模型服务，和公网对面的一个地址，不是同一
  个答案。

## S3 不是文件系统，而 agent 会立刻察觉

给每个租户持久化存储，最直白的办法是把 S3 桶里属于他的前缀挂起来。s3fs 和 `rclone mount` 都
试过。两者都不可用，原因与速度毫无关系：它们把文件系统调用映射成对象调用，而 S3 没有硬链接。

harness 通过「把临时文件硬链接覆盖到正式文件上」来原子替换会话日志。于是每一轮都立刻结束于

```
EIO: i/o error, link '…session.jsonl.zstd.tmp' -> '…session.jsonl.zstd'
```

而且一条 assistant 消息都没有。

**那个错误结论：** 认为在对象存储上做持久化这条路走不通。并不是。JuiceFS 是一个恰好把数据放在
对象存储里的**文件系统**——元数据存在事务型数据库里，所以硬链接、原子改名、文件锁都还是它们
本来的含义，对象存储只负责装数据块。错在从「S3 做不到这件事」推出「这件事在 S3 上做不到」，
而正确的修法是：别再拿这个问题去问 S3。

## 需要「取回来」的卷，不算卷

JuiceFS 的第一版为每个卷创建一个磁盘镜像，在沙箱创建时挂载。它能用，而且把这个平台存在的意义
毁掉了。

| | attach 耗时 |
|---|---|
| 不挂卷 | 0.39s、0.53s |
| 每次 attach 取磁盘镜像 | 7.92s、8.29s |
| 一次共享挂载 + 每卷一个 bind | 0.06s |

沙箱从快照还原不到半秒。于是 attach 路径上任何做拷贝、下载、或启动进程的动作，都会成为整个系统
里最慢的一环——差一个数量级。

所以每个节点只挂一个 JuiceFS 客户端，每个卷是它内部某个目录的 bind mount。bind 是一次系统调用：
没有字节移动，而且沙箱只看得见属于自己的那个目录。

## 挂载点撒谎的两种方式

两次都花掉一轮排查，而且形状相同：你最自然会去问的那个问题，本身就是会失败的调用之一。

**丢失了元数据库的客户端**仍然把挂载留在挂载表里，并对每一次调用回 `EIO`。`mountpoint` 说
「挂着呢」。检查必须是一次「会失败的读」，修复必须是卸载——往一个死挂载上再挂一次毫无作用。

**由已被替换的客户端建立的 bind** 对一切回 `ENOTCONN`，而且没有任何东西会重建它：挂载表里
还列着它，于是 attach 跳过重绑，把一个死挂载交给沙箱。租户的后端随后卡在 `mkdir '/workspace'`，
表现为 `session.create` 返回 500。

这一条试了三次才对，因为每一种探测本身都是会失败的调用：

- `mountpoint -q` 会把这种 bind 报告为**未挂载**，于是最显然的那道判断根本不触发。
- 对它 `mkdir -p` 会以 `ENOTCONN` 失败，在 `set -e` 下直接终止钩子，修复代码还没轮到执行。

真正可行的检测是读 `/proc/self/mounts`——内核从内存作答——再配一次会失败的调用：

```sh
if grep -qF " ${mnt} " /proc/self/mounts && ! ls "$mnt" > /dev/null 2>&1; then
    umount -l "$mnt"
fi
```

## 插件契约比产品需要的窄

CubeSandbox 的 VolumePlugin 在每个钩子里收到的，是一个 volume id 和一个名字。没有容量、没有
大小、没有自定义参数——而且文档明确写着：插件必须仅凭 volume id 定位后端资源，配置走配置文件
与环境变量。

这一条在相信之前验证了三遍：文档里的参数表、官方 Tencent COS 示例插件自己的参数解析、以及一次
带上 `capacity` 和 `labels` 的 API 调用——两个字段都被丢弃。

后果是按租户的配额没法从平台传进来。在上游支持在创建时传参之前，只能一个数字覆盖所有租户。
两种绕开它的设计都被否掉了，因为都比等更差：让网关直接设配额，等于把一个 120MB 的二进制和
元数据库凭据塞进那个负责认证租户的组件；让插件反过来问网关，则把一个通用插件绑死在某个产品的
HTTP 接口上。

## 按工作站尺寸设的默认值，落在共享节点上

JuiceFS 的缓存默认是 100 GiB，放在挂载者的家目录里。Cubelet 以 root 执行钩子，所以那是
`/root/.juicefs/cache`，落在 `/` 恰好所在的那个文件系统上——一个没有任何运维选择过的位置，
一个没人设过的上限，而且和其他所有东西共用一块盘。

现在两者都显式配置、且总是传入。这个大小只约束读缓存；writeback 暂存的写共用这个目录，由空闲
空间下限兜底——把它调得很小之前，值得先知道这一点。

## 时间到底花在哪

当时的直觉是元数据读是瓶颈——每次 `stat` 都要去 Postgres。测下来，这是错的。以每次小文件操作
计，本地盘是 0.06 ms：

| | 创建 | `stat` 冷 | `stat` 热 |
|---|---|---|---|
| 全部默认 | 38.13 ms | 1.0 ms | 0.007 ms |

元数据缓存本来就在生效：重复 `stat` 比冷读快 140 倍。之前那次得出相反结论的测量，用的是 shell
循环——每个文件 fork 一次 `stat`，进程开销比文件系统本身还大。

真正的开销在写，分两层：

- **每次 `close` 都在等一个对象上传完。** `--writeback` 在数据块落到本地暂存的那一刻就确认：
  38 ms → 17 ms。
- **每一次持久化的元数据提交都在等一次 WAL fsync**——实测 2.93 ms，关闭后 0.33 ms，而一次
  文件创建要花掉好几次：17 ms → 8.5 ms。

调高元数据超时，延长的是一个本就存在的缓存，而不是凭空造一个。它在这里安全，只是因为一个 volume
只挂给它租户的那一个沙箱——一个目录，一个写者。

## harness 对「自己在哪里被启动」是有意见的

其中两条花掉了实打实的排查时间：

- **dsh 从进程的工作目录取沙箱策略的 workspace 根。** 从 checkout 里启动它，就把 harness 的
  源码树变成了租户的工作区——而容器内是完全权限，于是 agent 的默认工作目录成了「运行它自己那个
  沙箱的代码」。
- **cordis 在加载时按包名解析插件**，因此一份组合需要哪些包无法从依赖图推导。`pnpm prune --prod`
  删掉过构建入口要 import 的 workspace 链接。后来改从 npm 安装时又发现，
  `@deepseek-ai/dsh-web-frontend` 沿依赖图从 CLI 包到达不了，必须显式点名。

还有一条制造出「插件加载了但什么都看不见」：**客户端模块注册表从配置树的 baseUrl 解析插件的
package.json**，且只扫描它能按名字解析到的包。按路径加载的插件只会挂载它的 host 那一半，
完全不贡献 client 半边。

`npm install <本地路径>` 是同样的故障、不同的成因：它建软链指回源码位置，Node 于是从软链指向的
地方去解析插件自己的依赖，而不是从 profile。共用的帧协议因此完全解析不到，隧道插件会死在第一次
import 上。`--install-links` 改为真实拷贝。

这两件事**构建都是绿的**。不去调用 `resolve()`，谁都看不出来。

## 「空闲」不等于「没有新请求」

沙箱在安静一段时间后被回收，因为每一个都是为一个人占着的一台机器的内存。第一版是从「最后一个
请求**开始**的时刻」算这段时间的。

而一次 agent 回合由一个请求发起，随后通过浏览器在它开始之前就已打开的 WebSocket 作答。一次长于
TTL 的回合会把自己的沙箱熬到过期，回收器在回答进行到一半时销毁它——就在租户看着输出流出的时候。

改用隧道流量判断能修好它，而这之所以可用，是因为协议里没有心跳：每一帧要么是请求、要么是响应、
要么是会话事件，所以安静就是真安静，被遗忘的浏览器标签页仍会按时被回收。将来任一端若加入保活帧，
这个信号就不再回收任何东西了。

## 唯一的能力信号，和无视它的那些界面

harness 很清楚容器里没有桌面：`host.describe().canOpenPath` 会去问平台，得到的是一台没有
显示服务器的 Linux。有两处界面查询了它并正确降级——agent preset 页把「打开位置」换成
「显示位置」，产出文件那一行干脆不渲染「在文件夹中显示」。其余的没有，而每一个都是在任何
沙箱里都不可能工作的控件：

- 设置里的「Open configuration file」判断的是 `settings.describe().hasDocument`，
  它算的是 `documentPath !== undefined`——文件是否存在，而它总是存在。`agentPreset.list`
  上同名的字段算的是 `canOpenPaths()`。两种写法必有一个是错的，而且从任一调用点都看不出
  是哪一个。
- `ui-conversation` 往自己的 chat view 里注入的 `openFile` 无条件调用 `host.openPath`，
  于是每一个产出文件 chip、每一处收尾消息里的行内路径引用，都是死链接。失败被一句
  `.catch(() => {})` 吞掉，注释说原生应用会自己弹错误框——这话没错，只是这里没有原生应用。

最锋利的证据说明这是漏了而不是取舍：deliverables 这个包在「在文件夹中显示」上判断了
`canOpenPath`，却没有在它上面两行的文件 chip 上判断。

先得出的错误结论：当时把它读成了「该藏起来的东西」，退出登录插件用一个空格子遮蔽了设置里的
那个动作，并且这样过了好几周。只有在没有任何东西可以替代时，藏起一个控件才是对的。这里有
东西可以替代——文档本身——而那次遮蔽还悄悄给一个只以一件事命名的包挂上了第三个主题，这正是
后来逼出 `dsh-sandbox-host` 与 `dsh-tenant-account` 拆分的原因。

真正够不着的是 chat view 的 `openFile`：它由拥有该视图的包注入，不是对外开放的插槽，插件
只能整个替换视图。已报到上游的
[discussion 2729](https://github.com/deepseek-ai/deepseek-harness/discussions/2729)——dsh 关闭了
issue，其 CONTRIBUTING 指定 Discussions 是报 bug 的地方，并声明目前不接受外部 PR，所以
一份报告就是本项目能做的全部。

## 共享的 `/api` 通道只接受一个 interceptor

dsh 提供两种加 RPC 端点的方式：`connection.rpc.intercept('/api', …)`，在浏览器本来就在
说话的那个通道上认领端点；以及 `connection.rpc.handle('/<name>', …)`，注册一个自己的通道。
前者显然更好——不用加路由、不用改网关、不用加 nginx location——而它不可用。`/api` 上只有
一个 interceptor 的位置，且已被 dsh 自己的 `typert-gateway` 在 base bundle 里占走。第二次
注册会抛错。

这个失败是响亮的，也就这一点好：它发生在组合期，而不是第一次上传时。但从契约上完全看不出
来——`intercept` 是有文档的公开方法，签名里没有任何地方说它只容一个——所以整套设计是在读到
`rpc-host.ts` 之前就照它写好了的。

自己一个通道最后反而是更好的形状。`/files` 在它经过的每一层都可见地是一个独立平面：一处
nginx location、网关路由里的一个分支、沙箱里的一条路由。藏在 `/api` 里的端点，这三样一样
都不是。

还要注意通道名的规则：`/^\/[A-Za-z0-9._~-]+$/`。只能一段。`/api/files` 不是合法通道，
所以一个平面无法嵌套在另一个之下。

## 没有 inject 的服务，会在「用它的地方」失败，而不是在挂载时

隧道插件 inject 了 `connection` 和 `apiProxy`，而它只有一个地方调用 `ctx.setTimeout`：
隧道断开后的重拨。cordis 拒绝一个读取方没有 inject 的服务——而且是在**读取处**拒绝，不是在
挂载时——所以那一行抛了异常，位置在一个 WebSocket close 回调里，那里没有任何东西接得住它，
于是租户的整个后端进程跟着隧道一起死了。

它活了好几周，靠的是它从外面看起来的样子：一个「网关重启时会跟着重启」的沙箱。这和人们对
网关重启的预期足够接近，以至于没人追问；验收套件也同意——它重启网关，然后检查活着的会话
仍然可用，而它确实可用，因为网关把自己刚刚杀掉的那个沙箱又建了一个。

它是被一次一次性探针翻出来的：用沙箱镜像对着一个连不上的网关地址启动。第一次 close 在几
毫秒内就到了，而不是永远不到，进程直接死在日志里。

有两点可以推广。一个只在稀有路径上被用到的依赖，是 happy path 证明不了的依赖，所以 `inject`
必须对着**每一处 `ctx` 的使用**来读，而不是对着插件启动时做的那几件事。以及：一个长得像正常
事件的故障，是最能活的那种——「跟着网关重启」不需要解释，于是它一直没被解释过。

## 组合器只有周围的座位，没有内部的

一个附件功能需要三样组合器没提供的东西，而每一样旁边都正好有一个它提供了的。

- **`+` 菜单只接受一个 source。** `inputTriggers.registerSource` 是加分组的正式途径，而 `+`
  调的是 `toggleSource('command', …)`，只把这一个名字塞进菜单。于是注册的 source 只在人敲
  `/` 时出现，永远不会出现在 `+` 下面——而人恰恰是在 `+` 里找「给这条消息加点东西」的。
- **卡片的位置是单格插槽，不是可叠加插槽。** dsh 的图片缩略图现在经由
  `conversation.input.attachments` 渲染，在卡片内部、编辑器上方。官方图片界面已经占着这个单格，
  通用文件在这里注册会替换图片轨道，而不是坐在它旁边。插件能叠加的每一个 input 区域仍在
  卡片外面。
- **用户消息只能整体替换。** `conversation.chat.node` 的 `user` 键可以遮蔽，但
  `UserMessageNodeView` 转手给了 `UserStyleBubble` 和 `MessageIconActions`，两者都没导出——
  所以想把附件在已发消息里画成 chip，就等于重写对话里最常用的那一行。

其中两样仍没有可叠加插槽能到达那个位置，所以插件通过 React portal 把自己的节点放过去：往
`+` 菜单**自己的面板里**加一个组，以及在不遮蔽图片轨道的前提下把插件自己的一个容器放到
它旁边。两者都已向上游反馈。

`+` 那个组一开始是画在真面板上方的第二个面板，读起来像一个菜单配两张卡片。放进去之后，样式
也顺带变诚实了：一行从活着的兄弟节点继承 hover、focus 和主题，而不是写死哈希类名。
这里有两件事必须做对。测量必须**跳过插件自己那一行**——和一个还没被样式化的行求交集，
结果是空，那次让这个组渲染成了一个光秃秃的按钮。以及必须等：候选项是异步取的，
最初几帧里只有一个 loading 行，还没有可测量的真实行。

卡片一开始是把后半句做错了的版本——搬的是 React 自己的节点。它会**让页面卡死**，而且只在那个
真正要紧的手势上：先上传，再发送。React 始终认为被搬走的节点仍是它渲染进去的那个容器的子节点，
于是第一次卸载时（组合器在「空会话→活动会话」时重建）对一个已经不在那里的节点调
`removeChild`，抛错，然后每次重试都再抛一次。portal 把所有权反过来：React 往一个它不掌管位置
的容器里渲染，而这一侧不掌管 React 渲染的任何东西。

Dsh 0.1.2 的编辑器迁移正好兑现了依赖这种结构的代价。它用 Lexical `contenteditable` 替掉了
textarea，所以上传会完成、通知也会到达 agent，但定位过程什么都找不到，卡片从未进入 DOM。
新的定位过程改用 Dsh 明确给出的 `data-input-scroll` 标记；浏览器验收会上传一个真实文件，等待
可见卡片出现，再把它移除。菜单仍按 ARIA 角色（`[role=listbox]` 和 `aria-expanded`）定位。
两个 portal 都不依赖哈希后的 CSS-module 类名，并且会在真正可叠加的座位出现时被删除。

第三样没有同样放进去。三条一起报在了 [discussion 2741](https://github.com/deepseek-ai/deepseek-harness/discussions/2741)。

## 「写进草稿」不等于「告诉 agent」

上传的第一版把提交后的路径写进了输入框草稿，理由是：在本地宿主上，人本来就会自己打这么一条
路径。但读起来是错的——人看着一条自己没打的路径出现在一个已经显示了同一个文件卡片的框里，
而且那条路径从此归他误编辑、误删一半。

想要的那个座位本来就存在。`agent.inbox.append('next-step', …)` 接受一条 `source.kind` 不是
`user` 的注入消息，队列把它投影为 `context`——认领前不可见，认领后渲染成一条 context 行，
而不是一段看起来像人自己说的话。`agent-instructions` 和 `goal-round-driver` 都在用它。
`inbox.remove(id)` 就是撤回，所以把卡片从消息上摘掉，通知也跟着走。

难发现的原因在于：草稿是组合器里插件唯一能写的部分，于是它看起来像是够到模型的唯一途径。而
inbox 在同一个会话的另一侧，够到它只需要客户端本来就有的 session id。

## 非 loopback 的浏览器，设置不会持久化

租户把主题改成深色，刷新，又变回浅色。没有任何报错，隧道一直连着，沙箱里的
`~/.dsh/settings.yaml` 始终是 0 字节。

判定发生在客户端，不在传输层。`dsh-client-ui-settings` 绑定每一个设置命名空间时写的是

```js
new SettingsScopeController(connection.api, spec, connection.isLoopback ? "host" : "memory")
```

而 `isLoopback` 取自页面自身的 hostname —— 只认 `localhost`、`[::1]`，以及 `127/8`
里的地址，别无其他。落到 `"memory"` 的那一侧，每次写入都只留在这个标签页里，刷新即弃。
它的文档注释把话说死了：*remote browsers remain process-local because settings RPCs
are loopback-only.*

这套部署确实让沙箱以为自己是被 loopback 调用的——隧道把每个转发请求都装扮成那样——但那是
**服务端**的一半。浏览器判断的是它自己地址栏里的东西，再多的转发也改不了。于是任何不通过
localhost 访问这套部署的租户，什么偏好都留不住：主题、语言、权限模式，一个都不会。

两个会话只差一个主机名。沙箱活着、文件存在、同样的点击在一个开在
`localhost` 的标签页里能正确写入——浏览器判断的是它自己地址栏里的地址，转发改不了这一点。

`dsh-tenant-account` 里本来就留着一条注释，说 onboarding 提示对「通过域名进来的租户」
留不住。那就是这件事，只是当时被看成某一条提示的怪癖，而不是所有设置的规则。

## 装 skill 的程序写在"你在哪"，而不是"你住哪"

OfficeCLI 的 `skills install` 会往它探测到的 agent 家目录里写，所以镜像给它一个临
时 `HOME`，再把结果搬走。`playwright-cli install --skills` 看着是同一类命令，其实
不是：它初始化的是一个**工作区**，把 `.claude/skills` 写在工作目录旁边。给了它一个
临时家目录、人却停在 `/`，它报告成功——"✅ Workspace initialized at `/`"、"✅ Skill
installed to `.claude/skills/playwright-cli`"——而紧跟着的 `mv` 在一个永远不会存在的
路径上失败了。

先得出的错误结论是：这个 CLI 拒绝安装，因为它在容器里以 root 运行、没有可安装的
agent。它装得好好的，只是装在了下一行去找的地方的上一层。

现在两个安装器各自拿到它真正读的东西——一个是家目录，一个是工作目录——并且后面都跟
一次对 frontmatter 的 `grep`。这一步把"文件不见了"变成构建失败，而不是变成一个
agent 永远不知道有这个工具的沙箱。

## 探针把自己的夹具堵死了

`verify/probe-browser-conformance.mjs` 先提供一个页面，再驱动浏览器去访问它。第一
版把那个页面放在探针自己的事件循环里提供，同时用 `spawnSync` 逐条跑命令——而
`spawnSync` 会一直堵住那个循环直到命令返回。于是浏览器来要页面的那段时间，夹具正好
是聋的：`open` 测到的是空白页，之后每条命令测的都是空气，报出九条并不存在的差异。

现在夹具是独立进程。这条更一般的形状值得记住：任何要应答请求的东西，都不能和
`spawnSync` 待在同一个进程里。

那个探针的第二次运行错在另一个原因，而且更难为情——上一轮手工实验留下的浏览器和夹
具还占着端口，于是探针接上的是一个正看着十分钟前那张页面的浏览器。现在只要其中任一
端口已经有人应答，它就拒绝启动。

## 字体属于引擎而不属于镜像的浏览器

Obscura 截的每一个中文页面都是一排排方框，而诊断经过了两个错误结论才到达正确的
那个。

第一个：容器缺 CJK 字体——显然如此，因为厂商镜像里一个字体文件都没有。但沙箱镜
像早就为 matplotlib 装了 `fontconfig` 和 `fonts-wqy-microhei`，生产环境本该没
事。事实上有事，于是有了第二个错误结论：引擎大概要字体放在某个特定位置。把中文
字体挂进 `/usr/share/fonts`，再挂进 `~/.fonts`，截图一个字节都没变。而与此同
时，拉丁文在一个不含任何字体的镜像里一直渲染得很好——这才是关键事实，却最后才被
注意到。

对二进制跑一遍 `strings` 定了案：Liberation 字体家族连同 Red Hat 的版权声明整个
内嵌在可执行文件里，它的 fontdb 从不加载系统字体。没有字体参数，也没有对应的
`OBSCURA_*` 环境变量。渲染完全按其构建的方式在工作，只是字体栈被封死在二进制内
部，镜像怎么摆布都够不到。这一条——加上直接拒绝重页面的任务预算——就是这个引擎退
役、换成走镜像自身 fontconfig 的 chrome-headless-shell 的原因。

能推广的有两条。一个渲染器可以把测试集的拉丁文那一半输出得完全正确，同时对另一
半完全无能，而每条命令都还在报告成功——探针里的 CJK 检查（两张只有中文字符不同的
截图，字节必须不同）就是为了让这件事下次大声地失败。以及：当把资源挂到某处不起
作用时，别再换位置试了，先问消费者到底读不读文件系统；四次挂载没回答的问题，
`strings` 一分钟就回答了。

## 文件的字节不是字符串对它们的看法

面板的图片预览在完好的文件上画出裂图。第一个、并且已经合进去的错误结论是：
e2b 客户端的 `files.read` 默认按文本解码，所以在共用的 `readFile` 上加上
`format: 'bytes'` 就能修好。那个默认值是真的，docker 路径也确实需要这个
参数。它在生产运行时上什么都没改。这个部署实际在讲的 CubeSandbox 客户端
早就收到了 `format: 'bytes'`，并且无视它——`read` 没有这个选项，永远走
`resp.text()`。对着租户沙箱量过：70 字节的 PNG 回来变成 86 字节，开头的
`0x89` 魔数变成 `EF BF BD`。

官方客户端曾经返回不了文件的字节。规则要求的答案是上游修复，而不是在旁边
再写一套协议。[Issue #1570](https://github.com/TencentCloud/CubeSandbox/issues/1570)
/ [PR #1571](https://github.com/TencentCloud/CubeSandbox/pull/1571) 补上了与
e2b 对齐的 `format` 表面（`text` / `bytes` / `blob` / `stream`）。在合入上游
`master` 之前，内置副本（`vendor/cubesandbox-sdk-0.3.0+82a807ab+e2b-read-format.tgz`）
按该 PR 构建。不要在它旁边再 fetch 一次 `/files`。

## 挂在 `/computer/` 下的 noVNC 必须显式给出 websockify 路径

Computer 面板嵌入的是 `/computer/vnc.html`。noVNC 把 WebSocket 拼成
`wss://host/<path>`，默认 `path=websockify`，于是浏览器连到站点根上的
`/websockify`——不在 nginx 的 location 里，也不在隧道剥 `/computer` 的路径上——
以 1006 失败。错误结论是隧道或 Upgrade 头坏了；其实 `GET /computer/vnc.html`
已经是 200。

在 iframe URL 上带 `path=computer/websockify`。隧道剥掉 `/computer` 后拨
`:6080/websockify`。控制台里 `/computer/package.json` 的 404 是另一件事，
且不挡连接：Debian 的 novnc 包在 `vnc.html` 旁没有 `package.json`。

## 复制一份核心包，就多了一份作用域身份

把定时任务插件漏声明的 tools 导入补成普通依赖后，导入检查通过了，会话创建却报
`deployment:persona` 重复。最初以为是上游 preset 坏了，实际原因是安装出了两套核心
依赖：`dsh-scope` 持有模块局部 Symbol，一份模块认不出另一份创建的 scope，于是把
preset 的人设注册到了全局。

插件现在把宿主包声明为 peer；镜像不另装 peer，而是在 profile 中链接宿主现有的 npm
包，不修改 harness 字节。`check-images.sh` 断言两边解析到同一个 tools 模块；会话与
真实对话验收再覆盖单纯导入检查看不到的作用域行为。

## Remote 升级不能沿用旧的 HTTP 探测

升级到 0.1.2-alpha.2 时，隧道最初仍轮询新的 `/api/remote.mux`，等待旧事件下行曾返回的
HTTP 426。错误假设是：只改路由名就能保留普通 GET 的行为。Remote gateway 单独注册升级
路由，普通 HTTP 则进入 RPC 处理器。于是 DSH 已经监听，隧道却始终不向网关报到，浏览器
一直等待一个其实已经完成的冷启动。

隧道现在先建立并关闭一条已认证的 WebSocket，再拨号到网关。它证明的是浏览器真正需要的
操作，不复制 Remote 帧协议。`verify/verify-ws.mjs` 检查公开入口的升级，
`verify/verify-turn.mjs` 在真实浏览器中检查模型回复能否流式显示。

已认证的升级在冷启动时仍然太早：首个 `session/modelCatalog` 虽然返回 HTTP 200，
却带着 `gateway/service-unavailable`，因为 `sessionController` 尚未激活。错误结论是
Remote 通道就绪就意味着业务服务也就绪；已有沙箱上的浏览器和定时任务检查调用得更晚，
因此都通过了。隧道现在把 `sessionController` 声明为启动顺序依赖；
`verify-cold-start.mjs` 只重建指定验收账号的沙箱，要求首个会话调用及随后的会话创建
直接成功，不插入等待，也不重试。

同一版本把模块资源改成 `/plugins/??...&rev=...`。旧的逐模块路径可以丢掉查询参数，新格式
却会因此把不同脚本写进同一个位置。静态采集现在为条目与批次保留完整 URL 身份，映射与补丁
覆盖由 `scripts/check-shell-assets.mjs` 检查。

运行时补丁最初在 `printUrl: false` 旁写了 `open: false`，误以为配置字段与 CLI 选项同名。
上游 schema 会保留未知字段，并静默补上默认的 `openBrowser: true`；补丁又覆盖了
`--no-open` 已设置的配置。无头验收仍然通过，生产后端却在启动时尝试打开浏览器。
补丁现改为 `openBrowser: false`，`check-images.sh` 使用发布包的 web-app schema 解析补丁，
检查实际生效的值，而不是只搜索 YAML 字面量。

## 卡片给的是浏览器画面，人要的是电脑画面

交接卡片当初用 CDP 给 agent 的 Chromium 截图。租户实际看到的每一张卡片，都是
一个空框加一句"浏览器尚未启动"。

错误的结论是 `/browser` 通道或者隧道坏了——因为面板的浏览器视图用的是同一批
端点，而它是好的。两者都没坏。桌面镜像里的 Chrome 是懒启动的，等 agent 第一次
用浏览器才拉起来，所以在那之前 CDP 根本不监听；而交接被抬起来的时刻，往往正在
那之前。更根本的是：交接是为"自动化走不下去的那个东西"抬起来的——KDE 的对话框、
终端里的提示、Chrome 从未打开过的那扇窗里的授权页。哪怕 CDP 有应答，页面截图
也不是一个人即将上手操作的这台电脑的样子。

现在卡片要的是整块 X 显示的一张 JPEG。在 1920x1080 的桌面上，`maim` 59ms 出图、
51KB，装机占 1.4MB。`scrot` 是同一个思路，代价是 59MB——imlib2 依赖 ghostscript
和 URW 字体集，只为几个这里永远不会打开的解码器；同一帧走 Node 的 zlib 编 PNG
是 226ms、282KB。

"接管"过去是派一个 DOM 事件，请工件面板打开它的电脑页签，于是登录表单被塞进
对话旁边 680px 宽的一列里。现在它把同一个 noVNC 画面铺满整个窗口，顶部只有一
条栏，agent 在等的那个答案就是那条栏上的一个按钮。

## 能推广的部分

- **快照装不下「之后才知道」的东西。** 一切与租户相关的，都必须在还原之后才抵达。
- **干净的环境是沉默的环境。** 任何给进程换爹的机制——这里是 envd——都会丢掉镜像设过的东西，
  而且不报错。
- **答案是「做不到」时，换个问题问。** S3 没有硬链接；建在 S3 之上的文件系统有。
- **attach 路径就是启动路径。** 亚秒级还原毫无价值，如果 attach 要八秒。
- **探测会以与被探测者相同的方式失败。** 先用内核从内存作答的东西检测，再用一次会失败的调用确认。
- **先测量再优化，并且怀疑自己的测量。** 第一次基准说元数据慢；它测的其实是 `fork`。
- **构建是绿的，不能说明解析没问题。** 软链、相对的 `file:` 路径、按名解析的插件，构建都正常，
  都在第一次 import 时失败。
- **只有在没有任何东西可以替代时，才藏起一个控件。**「Open configuration file」有替代品——
  文件的内容——而藏起它把这个发现推迟了好几周。
- **公开的方法不等于可用的方法。** `rpc.intercept` 有文档、有导出，而且已经被占了。
- **不存在的 CSS 变量会静默退回兜底值。** 要用 `getComputedStyle(document.body)`
  确认外壳真正定义了哪些名字再使用。
- **够得着的座位不一定是想要的座位。** 草稿是组合器里唯一可写的地方；agent inbox
  是另一处该查的地方。
- **绝不要搬 React 渲染出来的节点。** 给 React 一个容器加 portal；偷来的节点能撑到第一次卸载，
  然后让整个页面卡死。
- **`inject` 要对着每一处 `ctx` 的使用去读，而不是启动时的那几处。** 只在稀有路径上用到的
  服务，happy path 证明不了。
- **长得像正常事件的故障最能活。**「沙箱跟着网关重启」不需要解释，于是一直没被解释过。
- **给错东西的画面比没有画面更糟。** 交接卡片截的是 agent 的浏览器页面；人要的是
  自己马上要上手的那块屏幕，两者很少是同一扇窗。
