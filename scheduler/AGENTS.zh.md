# AGENTS.md — scheduler/

[English](AGENTS.md) | 中文

定时任务背后的那个时钟。为什么它是一个独立的服务而不是网关里的一个模块、以及三个部分
怎么分工,写在 [docs/scheduled-tasks.zh.md](../docs/scheduled-tasks.zh.md)。

## 它从不触发任何东西

这个服务只做两件事:唤醒机器,以及把没有发生的事记下来。**触发是
`packages/dsh-scheduled-tasks` 在沙箱里做的,而且它是唯一的触发方。**这不是优化,也不是
以后可以随手改掉的东西:每个租户只有一个触发方,重复运行就没有第二个发起方可言,而一次
运行是模型 token 和别人 workspace 上的写入。

由此得出两条,在没记住上面那条规则之前它们看起来都像 bug:

- **这里不看沙箱死活。**租户的沙箱起没起来是网关的知识,这个服务从不问。它在每一次到期
  都调 `/_internal/wake`;机器已经在跑,那次调用就是空操作,插件自己的定时器会做事。一个
  知道死活的调度器会忍不住去做决定,而做决定正是它不能做的事。
- **没人认领的到期被记为丢失,而不是重试。**`clock.js` 里的 `sweepMissed` 记一条 `lost`
  并推进序列。这既是"坏掉的沙箱不会变成沉默的沙箱"的保证,也是"一次错过不会永远每个 tick
  都去要那个租户的机器"的原因。

## 认领就是全部的并发故事

`POST /tasks/:id/claim` 往 `scheduled_runs` 插一行,`(task_id, occurrence_at)` 上的唯一键
决定谁来跑。其余的一切——序列推进、运行配额、启用检查——都在同一个事务里,压在对任务的
`SELECT ... FOR UPDATE` 之后。

**在认领时推进,绝不在完成时推进。**否则一次卡住的运行会让它自己那一次一直处于到期状态,
后面每一次都堵在它身后排队。

抢输的一方被告知 `already_claimed` 然后退下。这是一个普通结果——一台机器在它的前任还在
收尾时被重建,两边持有同一份列表——而不是值得记 error 的失败。

## 每条查询都按 username 收窄

包括那些本来就有主键的:`DELETE /tasks/:id` 仍然带 `AND username = $2`。id 是一个猜不到的
uuid,所以这对陌生人什么都不买;它买的是防住网关转发错租户,而那是唯一一个同时处理两种
身份的组件里的一行笔误。

这个服务没有任何办法核实谁是谁。它被那个能证明身份的组件通过一个共享密钥告知一个
username,而且是在一个租户根本不在的网络上,`compose.yml` 也没有给它任何宿主端口。密钥
不对或者缺失时答 **404 而不是 403**,理由和 `/_internal/account` 一样。

## 规则算术是纯的,所以它可以被检查

`src/rules.js` 不读任何没被交给它的时钟,也不写任何东西,所以
`scripts/check-rules.mjs` 能用一张用例表检查它,不需要数据库也不需要部署——包括两个夏令时
边界,而且是按墙上时钟断言的。这个功能的其余部分都需要一个运行中的部署,住在 `verify/`。

**保持它是纯的。**那里面任何一个函数一旦自己去读 `new Date()`,用例就不再可复现,这个检查
也就变成了"对今天的检查"。

## 表结构

`src/db.js` 里的一个字符串,每次启动用 `CREATE TABLE IF NOT EXISTS` 重跑一遍——和
[gateway/AGENTS.zh.md](../gateway/AGENTS.zh.md) 描述的它自己那份是同样的安排、同样的限制。
往里加一列,只会出现在空的部署上,别处不会。

这里唯一值得单说的是那个外键。`scheduled_tasks.username` 引用 `accounts(email)` 并级联,
这是这个服务伸进了一张它并不拥有的表。另一种做法的代价是:一个任务活得比它的主人还久,
继续为一个不再存在的账号唤醒机器、花掉 token——更糟的是,它属于下一个注册这个地址的人。

## 它不允许依赖什么

`e2b`、`@cubesandbox/sdk`、`ws`、`dockerode`、隧道协议——任何能够到沙箱的东西。它向网关要
一台机器,而对那台机器里发生什么一无所知。
`scripts/check-scheduler-boundary.mjs` 断言这一条,同一个检查也断言反方向:`gateway/src`
下面不许出现任何 cron 解析依赖或调度器的表名。
