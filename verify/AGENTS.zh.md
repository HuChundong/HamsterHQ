# AGENTS.md — verify/

[English](AGENTS.md) | 中文

验收套件：只能对着一个运行中的部署才能判定的那些事。它为什么活在 CI 之外，以及关于真实
地址的那条警告，在[根文件](../AGENTS.zh.md)里。这一页讲的是这里的一个检查该由什么搭起来。

## 一个检查长什么样

说 API 的东西叫 `verify-<property>.mjs`，需要在沙箱里开一个 shell 的东西叫
`verify-<subject>.sh`，而 `verify.sh` 是那个持有通过/失败计数的运行器。

开头的注释说明这个检查证明了哪条性质，以及这条性质为什么值得单独跑一次——
`verify-turn.mjs` 说出了整个套件所围绕的那个区别：其余一切证明的是管道会应答，而它证明
的是产品能用。

每个输入都是一个带默认值的环境变量，所以一次运行不需要参数，而一个名字不一样的部署不
需要改代码：

```js
const GATEWAY = process.env.GATEWAY ?? 'http://localhost:8080'
const USER = process.env.TURN_USER ?? process.env.VERIFY_ALICE ?? 'delivered+alice@resend.dev'
```

登录是 import 来的而不是重写一遍：`verify-login.mjs` 里的 `signIn` 是唯一知道登录时序的
地方。超时是有名字的常量——一次真实的模型 turn 被允许三分钟，而一个直接写在 socket 回调
里的数字，是当某个更慢的部署开始失败时没人找得到的数字。

## 两种运行时，都藏在 sandbox helper 后面

套件对两种沙箱运行时都能跑，而这两者没有任何可供检视的共同之处：在 `docker` 下一个沙箱
是本机上的一个容器，在 `cube` 下它是 Cube 网络里的一台机器，而只有 gateway 容器有凭证和
路由能够到它。所以关于一个租户沙箱的一切都走 `verify.sh` 里那些 `sandbox_*` helper——
列出归属、列出 handle、跑一段脚本、全部删除。一个直接去碰 `docker` 的检查，只在一种运行
时上有效，并且在另一种上悄无声息地跳过。

`cube` 那个 helper 是在 gateway 容器**里面**跑的，因为那是唯一同时具备客户端、Cube 两个
平面和到它们的路由的地方。它是在运行时被拷进去的，而不是烤进镜像：gateway 不携带任何验
证代码。

脚本以 base64 编码后送进沙箱，这样 `docker exec sh -c` 和 envd 的 `bash -l -c` 都不必去
扛套件自己的引号转义。

## 一个检查不可以假设什么

四条假设，每一条都曾经为真，然后就不为真了：

- **假设部署是空的。** 一个登录了控制台的运维也有一个沙箱。任何作用于"那个沙箱"的动作
  都要收敛到单个租户——曾经"取回来的第一个"这种做法，把一个标记写进了别人的机器。
- **假设存在一个管理员。** 邀请码是直接铸进表里的，好让登录不依赖某个管理员存在。它被
  包在一个 CTE 里以保持这条语句是 `SELECT`，因为 `psql` 会在返回行旁边往 stdout 打一个
  `INSERT 0 1` 的命令标签，而同时捕获两者的调用方拿到的会是一个后面粘着一行状态的验证码。
- **假设策略版本是已知的。** 它是从登录表单上读下来的，而不是写死在这里。升级那些文档不
  应该弄坏这个套件——而一个彻底不再征求同意的表单会在这里失败，那恰好是别的东西都抓不到
  的那类回归。
- **假设上一次运行清理干净了。** 铸新码之前先清掉未兑换的邀请码，因为每次运行都铸自己的。

验证码来自部署自己的数据库，永远不来自邮箱。那是运维权限，而不是一个用户拥有的入口：这个
码是一个只保留十分钟的秘密，而任何能读那个数据库的人本来就已经能铸出一个会话了。
